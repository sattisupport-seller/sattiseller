# План «хостинг пропал целиком» (К-21, часть 2, п.7)

Цель: Satti снова работает на новом сервере **другой казахстанской компании** за 1–2 часа. Пользователи теряют не больше суток данных (последняя ночная копия).

## Что держать вне хостинга (заранее, один раз)

| Что | Где хранить | Зачем |
|---|---|---|
| Копии базы (зашифрованные) | S3-совместимое хранилище **другой** казахстанской компании (OWNER_TODO п.8, К-23) | без них данных нет |
| Ключ шифрования копий `SATTI_BACKUP_KEY` | менеджер паролей владельца **и** офлайн-копия (бумага или флешка в сейфе) | без ключа копию не открыть |
| `SATTI_KASPI_KEY` (шифрование токенов Kaspi), `SATTI_TOTP_KEY`, `SATTI_BILLING_PEPPER` | там же, рядом с ключом копий | без них не расшифровать токены Kaspi, коды админки и отметки пробного периода |
| Остальные секреты (`deploy/.env` целиком), ключи Apple `.p8`, ключ Google JSON | менеджер паролей (вложения) | перенос без похода в консоли Apple и Google |
| Домен | регистратор **отдельно** от хостинга; вход с 2FA; код переноса (EPP/auth-code) записан | DNS можно перенаправить, даже если хостинг недоступен |
| DNS | TTL записей `A` для `api.<домен>` — **300 секунд** (5 минут) | переключение адреса быстро доходит до пользователей |
| SSH-ключ владельца | у владельца на компьютере и в менеджере паролей | вход на новый сервер |
| Код | GitHub (`origin`) и bundle в `satti-backups` | развернуть ту же версию |

Проверка раз в месяц (5 минут): ключ `SATTI_BACKUP_KEY` открывает последнюю копию (ежедневная автопроверка — часть 2, п.9, письмо при сбое).

## По шагам (1–2 часа)

| № | Шаг | Кто | Время |
|---|---|---|---|
| 1 | Заказать VPS Ubuntu 24.04 у **другой** казахстанской компании (от 2 ГБ памяти, SSD). Записать IP | владелец | 10–20 мин |
| 2 | `ssh root@<IP>`; скопировать код (`git clone` или bundle) в `/opt/satti`; `sudo ./deploy/deploy.sh setup satti ~/.ssh/id_ed25519.pub` — пользователь, только SSH-ключ, ufw, fail2ban, Docker | владелец или Claude Code по SSH | 10–15 мин |
| 3 | Вернуть секреты: `deploy/.env` из менеджера паролей (права 600), ключи `.p8` и JSON — в `server/data/secrets/` | владелец | 5 мин |
| 4 | Восстановить базу одной командой из хранилища копий: `./deploy/restore-latest.sh` (берёт последнюю копию из S3, проверяет и восстанавливает в новую базу; см. п.8) | владелец или Claude Code | 5–15 мин (зависит от размера) |
| 5 | Запуск: `./deploy/deploy.sh up` — миграции, запуск, проверка `/v1/health` | Claude Code | 5 мин |
| 6 | DNS: у регистратора `A api.<домен>` → новый IP. При TTL 300 — переключение за 5–10 минут. Caddy сам получит HTTPS-сертификат, когда DNS укажет на сервер | владелец | 5–10 мин |
| 7 | Проверка: `https://api.<домен>/v1/health` → 200; вход в приложение; заказы и прибыль на месте (сверить число заказов с последней сводкой); синхронизация Kaspi прошла; прайс-лист открывается по прежней ссылке (адрес прайса — по домену, он не меняется) | владелец + Claude Code | 10 мин |
| 8 | Внешний сторож (`deploy/watchdog.sh` или сервис проверки): адрес тот же, поменять ничего не нужно; убедиться, что письмо «сервер снова отвечает» пришло | владелец | 2 мин |
| 9 | Записать в REPORT: время каждого шага, что пошло не так | Claude Code | — |

Почему адреса для магазинов не меняются: уведомления App Store и Google Play, прайс-лист Kaspi и ссылки в письмах идут на **домен**, а не на IP. Поэтому после шага 6 они работают без правок в консолях.

## Что теряется

- Изменения после последней ночной копии (до 24 часов): заказы Kaspi за это время **догрузятся сами** — синхронизация читает от курсора и перечитывает 60 дней ночью. Вручную введённые затраты и остатки за этот день — ввести заново.
- Очередь пушей и счётчики лимитов — не важны, создаются заново.

## Репетиция

Репетиция переезда — в первый день после покупки сервера (часть 2, п.14, LAUNCH.md): те же шаги на втором тестовом сервере с замером времени. До репетиции план считается непроверенным.
