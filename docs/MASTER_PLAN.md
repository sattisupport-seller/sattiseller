## 2. Начало каждой сессии («продолжаем»)

1. Прочитай `docs/HANDOFF.md`, затем нужные разделы этого файла и `docs/LAUNCH_PLAN.md`.
2. Выполни `git status` и проверь текущую ветку. Если есть незакоммиченные изменения — сверь их с HANDOFF, доведи пункт до зелёного состояния и закоммить. Ничего не откатывай и не удаляй молча.
3. Базовая проверка: тесты сервера и приложения, ruff, tsc. Если что-то красное осталось с прошлой сессии — сначала исправь это.
4. Проверь, что появилось у владельца:
   - `git remote -v` — подключён ли GitHub;
   - `docker --version`, `adb --version`, список эмуляторов — установлены ли Docker Desktop и Android Studio;
   - появились ли непустые переменные из раздела 7 в `.env`. Проверяй командой, которая отвечает только «да/нет» (например, PowerShell `Select-String -Path <путь к .env> -Pattern '^ИМЯ=.+' -Quiet`). Файл `.env` целиком не открывай, значения не выводи и не записывай никуда.

   Если что-то появилось — выполни соответствующую строку раздела 7.2 и сними ⛔ с пунктов, которые это разблокирует.
5. Возьми первый невыполненный и незаблокированный пункт по порядку раздела 5 и сразу работай — без пересказа плана и без вопросов.
6. Если незаблокированных пунктов не осталось — не придумывай работу. Выведи коротко список из `OWNER_TODO.md` (что сделать владельцу, по порядку) и остановись.

После автоматического сжатия контекста снова прочитай `HANDOFF.md` и текущий пункт плана.

## 4. Решения владельца (действуют, не переспрашивать)

**Продукт**
- Satti Seller — мобильное приложение для продавцов Kaspi.kz. Выпуск только в Казахстане. Пользователи 18+.
- Подписка 9 900 ₸ в месяц, пробный период 14 дней — через App Store и Google Play.
- Вход только через Apple и Google. Вход по коду на почту — только для разработки и тестов, в продакшене выключен.
- Интерфейс — русский и казахский. Юридические тексты — только русский.

**Данные и закон**
- Серверы и базы — только в Казахстане.
- Данные покупателей хранятся, но перед отправкой ИИ маскируются: имена, телефоны, адреса, ИИН, номера карт, словарь из заказов.
- Согласия: одна обязательная галочка при регистрации; отдельное согласие на передачу данных ИИ (Anthropic, США) — при первом открытии помощника.
- Пометка «Ответ создан ИИ» на каждом ответе помощника.
- Данные владельца в документах — только через переменные (владелец, email поддержки). Без телефона и адреса.

**Техника**
- Продакшен — PostgreSQL.
- Лимиты — вариант A: на PostgreSQL — таблица `rate_limits`, на SQLite — в памяти процесса. `api.py` ради этого не менять.
- Черновики ИИ входят в общую квоту 30 запросов в день.
- Почта — универсальный SMTP-адаптер; в разработке — папка outbox.
- Бэкапы — ежедневно, хранить 14 дней, с шифрованием, копия во второе хранилище (S3-совместимое).
- Демо живёт 24 часа от создания; не больше 3 новых демо и сбросов в сутки с одного устройства.
- Ориентир нагрузки — до 1000 продавцов в первые 6 месяцев.
- Повторный пробный период через другой email — принятый риск. Вход через Google и Apple с одним подтверждённым email — один аккаунт.
- Kaspi: цены и остатки — только через XML-прайс продавца; заказы — опросом по расписанию (вебхуков нет); токен продавца — только в зашифрованном виде.
- `# nosec` разрешён только для трёх подтверждённых ложных срабатываний bandit, с обоснованием в строке.

## 5. Фаза А — порядок работ (без аккаунтов владельца)

Выполняй строго по порядку. Если пункт требует аккаунта, ключа, прав администратора или решения владельца — отметь ⛔ с причиной, добавь шаги в `OWNER_TODO.md` и переходи к следующему пункту. Всё, что можно сделать до блокировки (код, моки, тесты), сделай.

### Этап 1. Остатки исправлений

- **1.15** Общие лимиты (вариант A), включая счётчик демо по устройству.
  *Готово:* тесты лимитов зелёные на SQLite и PostgreSQL; два процесса на PostgreSQL делят один лимит.
- **1.14** Защита ИИ от инструкций в данных: обрезка названий товаров и отзывов, разделители и пометка «данные, не инструкции» при передаче модели, сильные тесты на инъекцию через названия и отзывы.
  *Готово:* тестовые атаки не меняют поведение помощника.
- **1.11** Тесты экранов: сначала нажатия и формы в критичных сценариях (согласие, вход, импорт, удаление аккаунта, подписка, экспорт), затем покрытие `src/app` ≥ 70%.
- **1.19** Согласия по решению владельца. Проверь, сделано ли; если нет — сделай:
  - одна обязательная галочка при регистрации, не отмечена заранее, с сохранением версии документа и времени;
  - повторное согласие при новой версии документов;
  - ссылки на условия и политику на экране входа и в настройках.
- **1.16** Демо из шаблона одним `INSERT ... SELECT` вместо генерации заново; повтори нагрузку 10/50/100 на PostgreSQL.
  *Ориентир:* при 100 пользователях нет 5xx, медиана < 1 с. Если на ноутбуке недостижимо — объясни причину и перенеси замер на сервер (Фаза Б).
- **1.17** Производительность на реальных объёмах (AUD-12): магазин с 10 000 заказов.
  *Ориентир:* при 20 пользователях p95 < 500 мс. При необходимости — агрегаты в базе или кэш с инвалидацией при записи.
- **1.4** (дозавершить после 3.6) Письмо владельцу при 80% и 100% бюджета ИИ. Адрес — переменная `SATTI_OWNER_ALERT_EMAIL`.

### Этап 2. Kaspi на моках

- **2.1** Клиент Shop API строго по официальной документации (guide.kaspi.kz/partner/ru/shop/api): заказы, состав заказа, товары; 401/429/5xx — повторы с паузой; соблюдение лимитов. Допущения — в `docs/kaspi-assumptions.md`.
- **2.2** Опрос заказов по расписанию: инкрементально, без дублей, с продолжением после сбоя.
- **2.3** XML-прайс для цен и остатков по формату Kaspi; ссылка на прайс для кабинета продавца.
- **2.4** Токен: только в зашифрованном виде, проверка при подключении, отключение в один шаг, удаление вместе с аккаунтом.
- **2.5** Мок-сервер Kaspi: 1, 100 и 10 000 товаров; возвраты, отмены, частичные возвраты.
- **2.6** Флаг `KASPI_ENABLED` (по умолчанию выключен).
- **2.7** Экраны в приложении: подключение магазина (ввод токена и ID продавца, подсказка, где их взять в кабинете), статус синхронизации, понятные ошибки (токен отозван, Kaspi недоступен), отключение.
- **2.8** Сквозной тест на моке: подключение → загрузка товаров и заказов → расчёт прибыли → XML-прайс → отключение → удаление данных.

### Этап 3. Оплата, вход, пуши, ИИ, почта — готовность к ключам

Всё на моках и записанных примерах ответов. Ключи — только из `.env`.

- **3.1** Покупки:
  - клиент — react-native-iap или совместимая с Expo dev build библиотека;
  - экран подписки: цена, период, условия автопродления, ссылки на условия и политику;
  - кнопка «Восстановить покупки», ссылка на управление подпиской;
  - серверная проверка: App Store Server API и Google Play Developer API, вызов `activate_paid`, пробный период через магазин.
- **3.2** Уведомления магазинов: App Store Server Notifications V2 и Google RTDN (Pub/Sub) — продление, отмена, возврат, льготный период; обработка идемпотентная.
- **3.3** Вход Apple и Google: клиент и сервер, все идентификаторы из `.env`.
  Сверь задачу 21 ТЗ («один телефон», перенос на другой телефон с подтверждением) с ADR-0004 и решением «вход только Apple/Google». Если требование действует — сделай на моках (App Attest / DeviceCheck на iOS, Play Integrity на Android). Если противоречит решениям — запиши в `PROPOSALS.md` и продолжай.
- **3.4** Пуши: expo-notifications, регистрация токена устройства на сервере, сводка по понедельникам, тихие часы, настройки уведомлений в приложении. Разрешение запрашивать тогда, когда пользователю понятно, зачем оно.
- **3.5** Живой ИИ: провайдер Anthropic через официальный SDK, ключ `ANTHROPIC_API_KEY`, модель — из переменной; таймауты, повторы, ограничение длины; стоимость по ценам из конфига (не зашивать в код); бюджет и выключатель работают; маскировка проверена на реальном формате запроса.

- **3.7** `.env.example`: каждая переменная — назначение, пример, где получить, обязательна ли в продакшене.
- **3.8** Оценка качества ИИ (ТЗ, задача 25): набор вопросов продавца с ожидаемыми фактами, автоматический прогон, порог ≥ 90%. Сейчас — на моке, с реальным ключом — в Фазе Б.
- **3.9** События аналитики (ТЗ, задача 30): по списку из ТЗ, без персональных данных, хранение в своей базе, просмотр в админке. Если политика конфиденциальности этого не описывает — предложение правки в `PROPOSALS.md` (юридические тексты сам не меняй).
- **3.10** Оповещения владельцу (ТЗ, задача 29): канал — email. WhatsApp — только после решения владельца (раздел 9).

### Этап 4. Развёртывание

Пиши и проверяй всё, что можно без Docker. Запуск Compose — после установки Docker Desktop владельцем (⛔ до этого).

- **4.3** `deploy.sh` для чистого Ubuntu 24.04: отдельный пользователь, вход только по SSH-ключу, запрет входа root и по паролю, ufw (22, 80, 443), fail2ban, автоматические обновления безопасности, синхронизация времени. Файлы секретов — с правами 600.

- **4.6** Caddy: HTTPS автоматически, заголовки безопасности, лимит размера запроса, доверенный прокси для лимитов (`SATTI_TRUSTED_PROXIES`).
- **4.7** Выпуск и откат: обновление сервера одной командой, бэкап перед каждой миграцией, миграции при выпуске, откат на предыдущую версию.

## 8. Правила работы

### 8.1 Остановки
- Не останавливайся ради отчёта после каждого пункта: отметь пункт в LAUNCH_PLAN, обнови HANDOFF и иди дальше.
- Пункт заблокирован → ⛔ с причиной, шаги в OWNER_TODO, следующий пункт.
- Спрашивай владельца, только если нельзя сделать вообще ничего.
- Для широкого поиска по коду и чтения больших файлов используй субагентов, чтобы основной контекст дольше не заполнялся.

### 8.2 Качество
- Ошибка → сначала тест, который её воспроизводит, потом исправление.
- После каждого пункта: тесты сервера (SQLite) и приложения, ruff, tsc. После каждого этапа — дополнительно тесты сервера на PostgreSQL.
- Коммит — только при зелёном результате. Если pre-commit hook (tsc, ruff, быстрые тесты) ещё не настроен — настрой, без прав администратора.
- Не ослабляй тесты и не ставь xfail или skip ради зелёного результата.
- Не выдумывай результаты. Что не проверено — так и пиши.
- Внешние API — строго по официальной документации. Всё, что требует ключей, — на моках с пометкой «проверено только на моке».
- Пороги покрытия: сервер в целом и критичные модули ≥ 90%, экраны `src/app` ≥ 70%.
- Команды и инструкции — для Windows.

### 8.3 Сохранение и git
- Рабочая ветка — текущая (сейчас `qa/full-check`) до пункта 6.7.
- Коммит после каждого законченного пункта, сообщение на русском. Разные пункты в одном коммите не смешивать.
- После каждого этапа — `git bundle create --all` в `C:\Users\user\Desktop\satti-backups\` (дата + номер этапа), затем `git bundle verify`. Храни 5 последних копий. После подключения GitHub — ещё и push.
- Перед рискованным действием — коммит-точка «перед <действие>».
- Запрещено: `git reset --hard`, `git push --force`, `git clean -fdx`, переписывание истории.

### 8.4 Уборка (только в пункте 6.1)
1. Сначала `CLEANUP_PLAN.md`: что удалить, почему не нужно, как проверено (поиск ссылок и импортов, git log), риск.
2. Удалять только файлы из git (`git rm`) — они восстанавливаются из истории. Неотслеживаемые — перенести в `_to_delete/` вне проекта и перечислить владельцу.
3. Небольшими группами: удаление → все тесты → запуск сервера и приложения → коммит «уборка: <что>». Сломалось — откатить группу.
4. Вручную не трогать `node_modules`, `.venv`, конфиги сборки, lock-файлы.

### 8.5 Защищённые файлы — без разрешения владельца не изменять
- `.env` и `.env.*`, `server/data/` (secret_key, база, outbox, secrets), ключи и сертификаты.
- `docs/legal`, ТЗ, `AUDIT_REPORT.md`, `QA_REPORT.md` (QA_REPORT обновляется только в 6.3).
- Существующие ADR (новые ADR создавать можно).
- Существующие миграции alembic (новые миграции создавать можно и нужно).
- Золотые тесты и их эталонные данные, таблица казахских строк, `assets/`.
- Этот файл (`docs/MASTER_PLAN.md`) меняет только владелец; предложения — в `PROPOSALS.md`.
- `CLAUDE.md` — только раздел-указатель из пункта 0.

Разрешено создавать и обновлять: LAUNCH_PLAN.md, HANDOFF.md, OWNER_TODO.md, PROPOSALS.md, OPERATIONS.md, STORE_COMPLIANCE.md, DEVICE_CHECKLIST.md, FINAL_REPORT.md, LAUNCH.md, `docs/store/`, README (разделы, связанные с изменениями).
