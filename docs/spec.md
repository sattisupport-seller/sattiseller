**Версия:** 2.0

## 1. Резюме

Satti Seller помогает продавцу маркетплейса Kaspi понять, сколько он зарабатывает на каждом товаре:

- показывает продажи, заказы, возвраты и расчётную прибыль за период;
- считает прибыль по каждому товару после закупки, комиссии и доставки;
- честно показывает, каких данных не хватает (например, закупочной цены);
- принимает закупочные цены файлом или вводом с телефона;
- отвечает на вопросы о магазине через ИИ-помощника — с цифрами из серверного отчёта и объяснением причин;
- готовит черновики описания товара и ответа покупателю.

Приложение ничего не меняет в Kaspi: не меняет цены и остатки, не принимает и не отменяет заказы, не пишет покупателям, не публикует карточки.

**Пользователь:** продавец Kaspi примерно с 20–500 товарами, который хочет контролировать магазин с телефона.

## 2. Этапы выпуска

| Этап | Что внутри | Где доступно | Условие перехода дальше |
|---|---|---|---|
| A. Прототип | демо-магазин, все экраны, импорт, помощник на синтетических данных | TestFlight (iOS), внутреннее и закрытое тестирование Google Play | интервью с продавцами и решение «продолжать» (`docs/owner.md`) |
| B. Закрытая бета | аккаунты, свои затраты, реальные заказы через подключение Kaspi или импорт отчёта | TestFlight и закрытое тестирование, приглашённые продавцы | сервер и данные в Казахстане, юридические документы, ответы Kaspi |
| C. Публичный релиз | всё из этапа B, проверенное на бете | App Store и Google Play | одобрение обоими магазинами |
| D. Платная версия | подписка через покупки в приложении | App Store и Google Play | решение по цене после интервью |

Правило: в публичные магазины выходит только версия с реальной пользой (этап C). Apple не принимает в App Store демо- и бета-версии — для них есть TestFlight. Демо-режим остаётся внутри публичной версии как способ попробовать приложение без подключения.

## 3. Функции

Ниже — что может пользователь. Как это выглядит — в `docs/design.md`, раздел 12.

### 3.1 Доступ

- Демо без регистрации: отдельная песочница на каждое устройство (раздел 9).
- Аккаунт: вход по email и 6-значному коду (без пароля). При первом входе — название магазина, часовой пояс, язык.
- Выход; удаление аккаунта внутри приложения с подтверждением кодом.
- Один магазин на аккаунт в первой версии; модель данных допускает несколько.

### 3.2 Обзор

- Период: сегодня, 7, 30, 90 дней, свой период; сравнение с предыдущим равным периодом.
- KPI: чистые продажи, расчётная прибыль (с покрытием), заказы, возвраты и отмены — с дельтами.
- График прибыли или продаж по дням с линией прошлого периода.
- «Требует внимания»: товары в минус, товары без закупки, товары с большим числом возвратов.
- Лучшие товары, вход в помощника, время данных.
- «Подробно о прибыли»: лесенка от продаж до прибыли магазина, покрытие, недостающие данные.

### 3.3 Заказы

- Список по дням, поиск по номеру и товару, фильтры по статусу, период.
- Карточка заказа: товары, суммы, комиссия, доставка, расчётная прибыль, возвраты, источник каждой суммы.
- Только просмотр. Данных покупателя нет.

### 3.4 Товары и затраты

- Список с поиском, фильтрами («в минус», «нет закупки», «много возвратов», «без продаж») и сортировкой.
- Покрытие: сколько товаров с полными данными.
- Карточка товара: продажи, прибыль, маржа, экономика одной продажи, затраты на единицу с историей версий, возвраты.
- Изменение затрат с выбором даты начала действия (раздел 6.5 и 7.5).
- Быстрый ввод закупки для товаров без неё — прямо с телефона.
- Комиссии по категориям и расходы на рекламу.

### 3.5 Импорт затрат

Файл XLSX или CSV на основе прайс-листа из кабинета Kaspi: выбор файла на телефоне, сопоставление колонок, проверка с ошибками по строкам, применение, отмена последней загрузки (раздел 7).

### 3.6 Помощник

- Вопросы о магазине обычными словами на русском и казахском.
- Ответ: текст, период, время данных, основания с цифрами из отчётов, недостающие данные, уверенность, переходы к товару.
- Согласие на передачу данных внешнему ИИ-сервису до первого вопроса.
- Оценка ответа и жалоба на ответ внутри приложения.
- История диалогов с удалением; дневной лимит вопросов.
- Черновик описания товара (текст и до 5 фото) и черновик ответа покупателю — только копирование, без публикации.

### 3.7 Профиль и настройки

Язык (как в системе / русский / казахский), тема (как в системе / светлая / тёмная), уведомления, отзыв согласия на ИИ, помощь, поддержка, документы, выход, удаление аккаунта.

### 3.8 Позже

- Уведомления: товар ушёл в минус, еженедельная сводка (этап B), новые заказы (после подключения Kaspi).
- Подключение Kaspi по ключу доступа (этап B, за флагом).
- Подписка (этап D).

## 4. Технологии и архитектура

### 4.1 Общая схема

```text
Телефон (Expo-приложение)  ──HTTPS / JSON──►  Сервер (Python)  ──►  БД
        экраны, кэш,                           расчёты, импорт,      PostgreSQL
        безопасное хранение сессии             демо, ИИ, Kaspi
                                                     │
                                                     └──►  внешний ИИ-сервис (только с сервера)
```

Приложение не считает деньги и не хранит секреты. Ключи ИИ-сервиса и Kaspi есть только на сервере.

### 4.2 Мобильное приложение

- **Expo** (React Native) на текущей стабильной версии SDK — на момент написания SDK 58 с React Native 0.88. При старте работы взять актуальную стабильную версию.
- **TypeScript** в строгом режиме.
- **Expo Router** — навигация по файлам: вкладки, стеки, модальные экраны, листы.
- Сборка и публикация — через сервисы Expo (EAS): сборки для iOS делаются в облаке, Mac не нужен.
- Состояние сервера — кэширующий слой запросов с повторами и обновлением при возврате в приложение; формы — с валидацией схемами.
- Безопасное хранилище платформы (Keychain / Keystore) — только для токенов сессии.
- Шрифт Inter встроен в приложение; иконки Lucide.
- Конкретные библиотеки выбирает Claude Code. Ограничения: совместимость с текущим Expo SDK, без платных SDK, без рекламных и трекинговых SDK, без библиотек, требующих лишних разрешений.

### 4.3 Сервер

- **Python 3.12+**, **FastAPI** + Pydantic, SQLAlchemy 2 + Alembic.
- **PostgreSQL**; для локальной разработки допускается SQLite (деньги — только целые тиыны).
- Описание API в OpenAPI; типы и клиент для приложения генерируются из него, чтобы приложение и сервер не расходились.
- Код из версии 1.2 (`money`, `finance`, `reports`, `demo`, `imports`, `ai`) переносится в сервер без изменения формул; golden-тесты должны проходить.
- Если в репозитории уже есть рабочий сервер на Flask, допустимо оставить Flask и превратить его в JSON API. Решение фиксируется в `docs/adr/0002-mobile-and-api.md`.
- Веб-страницы, шаблоны, HTMX и PWA из версии 1.2 удаляются: их заменяет мобильное приложение. Остаётся простая веб-страница для удаления аккаунта (требование Google Play) и, при необходимости, страницы документов.

### 4.4 Структура репозитория

### 4.5 Окружения

| Окружение | Сервер | Данные | Сборки |
|---|---|---|---|
| development | локальный | демо | сборка для разработки на телефоне разработчика |
| preview | тестовый сервер по HTTPS | демо и тестовые аккаунты | TestFlight, внутреннее и закрытое тестирование Google Play |
| production | сервер в Казахстане | реальные | App Store, Google Play |

Адрес сервера задаётся профилем сборки. Секретов в приложении нет ни в одном окружении.

### 4.6 Обновления приложения

- Версия приложения — по схеме «мажорная.минорная.исправление» (1.0.0); номер сборки растёт автоматически.
- Обновления «по воздуху» (без магазина) — только для исправлений ошибок, не меняющих назначение приложения. Новые функции — только новой сборкой через проверку магазинов.
- Сервер отдаёт минимальную поддерживаемую версию: если версия приложения ниже, показывается экран «Обновите приложение».

## 5. API сервера

Внутренний API Satti, версия `/v1`. Это не методы Kaspi.

### 5.1 Общие правила

- Только HTTPS. Формат — JSON, кодировка UTF-8.
- Деньги — целые тиыны в полях с суффиксом `_minor` и полем `currency: "KZT"`. Ставки, доли, маржа и дельты — целые базисные пункты (`_bp`, 10% = 1000). Дробных чисел для денег нет.
- Даты и время — ISO 8601 со смещением; календарные периоды — даты в часовом поясе магазина.
- Пагинация — курсором, не больше 50 записей за запрос.
- Ошибка: `{"error": {"code": "...", "message": "...", "error_id": "..."}}`; `message` — на языке пользователя; без stacktrace и внутренних данных.
- Язык — из заголовка `Accept-Language` (`ru` или `kk`).
- Ограничение частоты: вход — не больше 5 запросов кода в час на email и IP; импорт — 10 в час; ИИ — по дневному лимиту.
- Каждый запрос проверяет, что пользователь имеет доступ к этому магазину.

### 5.3 Сессии

- Вход по коду: код из 6 цифр, действует 10 минут, не больше 5 попыток; затем — новый код.
- Короткоживущий токен доступа (около 15 минут) и токен обновления (около 30 дней) с ротацией; на сервере хранятся только хеши.
- Демо-сессия — анонимный токен, привязанный к установке приложения. Песочница удаляется через 30 дней без активности.
- При создании аккаунта из демо-режима демо-данные не переносятся в аккаунт.
- Для проверки в App Store и Google Play — отдельный аккаунт проверяющего с фиксированным кодом, который работает только для этого адреса и только на нужном окружении.

## 6. Финансовая модель — только детерминированный код

**Все суммы и агрегаты считает сервер. Приложение только показывает. LLM не выполняет арифметику и не придумывает числа.**

### 6.1 Деньги

- Целые тиыны: `int` в коде, `BigInteger` в БД. 1 ₸ = 100 тиынов.
- Ставки — целые базисные пункты: 10% = 1000 bp, 7,5% = 750 bp.
- `float` для денег запрещён. Входные значения разбираются через `Decimal(str(value))` и переводятся в тиыны с проверкой, что дробной части не осталось.
- Колонки `Numeric` / `Decimal` для денег не используются (SQLite хранит их неточно).

### 6.2 Округление

- `ROUND_HALF_UP` — половина округляется от нуля, как в Excel. Банковское округление не используется.
- Комиссия считается и округляется по каждой строке заказа до тиына; итоги — суммы округлённых строк.
- В интерфейсе — целые тенге с тем же правилом; проценты — один знак после запятой.

### 6.3 Компоненты затрат

| Компонент | Уровень | Источник | Где учитывается |
|---|---|---|---|
| Закупочная цена | единица товара | импорт, ручной ввод | себестоимость |
| Доставка до продавца | единица товара | импорт, ручной ввод | себестоимость |
| Упаковка и прочие на единицу | единица товара | импорт, ручной ввод | себестоимость |
| Комиссия маркетплейса | строка заказа | ставка категории | расход строки |
| Доставка покупателю за счёт продавца | строка заказа | демо; позже — данные Kaspi или правило-оценка | расход строки |
| Реклама и прочие расходы магазина | магазин, период | ручной ввод | только прибыль магазина |
| Налоги | — | не считаются | подпись «до налогов» |

Строка «полная», если известны себестоимость, комиссия и доставка покупателю (фактическая, оценка по правилу или «не применяется»). Оценка делает строку полной, но с пометкой «оценка».

### 6.4 События и даты признания

- `completed_sale` — дата выдачи заказа `completed_at`; по ней выбираются версия затрат и ставка комиссии.
- `cancelled` — не продажа; показывается в «Отменах».
- `returned` / `partial_return` — дата подтверждения возврата; уменьшает показатели того периода, куда попал возврат. Прошлые периоды не пересчитываются.
- `pending` / `in_progress` — только в «Сумме заказов».
- Если хотя бы один компонент возврата неизвестен (возврат покупателю, возвращённая комиссия, возвращённая доставка, обратная доставка, годен ли товар), прибыль строки — `unknown`, строка выпадает из точного итога.

### 6.5 Формулы

```text
revenue_i     = цена × количество
landed_cost_i = себестоимость единицы на дату completed_at × количество
commission_i  = round_half_up(revenue_i × rate_bp / 10000)
profit_i      = revenue_i − landed_cost_i − commission_i − доставка_i

возврат: revenue_i −= возврат покупателю; commission_i −= возвращённая комиссия;
         доставка_i += обратная доставка − возвращённая доставка;
         landed_cost_i −= себестоимость × вернувшееся количество (если товар годен)

complete_set       = строки, где известны все компоненты
coverage           = чистые продажи complete_set / чистые продажи всех строк
margin             = прибыль complete_set / чистые продажи complete_set
прибыль магазина   = прибыль по товарам − расходы магазина за период
```

- Числитель и знаменатель маржи — по одному набору. Делить прибыль полного набора на все продажи запрещено.
- Сравнение периодов — по товарам, у которых данные полные в обоих периодах; остальные перечисляются отдельно.
- Расходы магазина распределяются по дням пропорционально; остаток округления — на последний день записи.
- Себестоимость берётся из версии затрат, действующей на дату продажи; версия без даты начала действует с начала истории.

## 7. Импорт затрат

### 7.1 Сценарий с телефона

1. Продавец скачивает прайс-лист из кабинета Kaspi на компьютере («Управление товарами → Прайс-лист → Скачать в Excel»), дописывает колонки затрат и сохраняет файл туда, где откроет его с телефона (облачный диск, почта, мессенджер).
2. В приложении выбирает файл системным выбором документов.
3. Сервер распознаёт колонки; если не смог — пользователь сопоставляет их вручную.
4. Проверка → применение → возможность отменить.

Альтернатива для телефона — «Быстрый ввод закупки»: список товаров без закупки с полем цены у каждого.

### 7.2 Шаблон

`Артикул; Закупка, ₸; Доставка до склада, ₸; Упаковка, ₸; Прочее, ₸; Действует с` — все суммы на единицу товара. Доставка покупателю в шаблон не входит. Названия колонок прайс-листа Kaspi не хардкодятся: до получения пустого шаблона Kaspi — сопоставление в интерфейсе с запоминанием выбора.

### 7.3 Форматы и лимиты

- XLSX (первый или выбранный лист, чтение значений без формул) и CSV (UTF-8 с BOM или без; при ошибке — cp1251 с показом превью текста). XLS и XLSM не принимаются.
- Разделитель CSV — запятая или точка с запятой, определяется автоматически.
- Файл до 5 МБ, до 5 000 строк, распакованный XLSX — до 50 МБ (проверка до разбора).
- Файл удаляется сразу после разбора; его содержимое не пишется в логи.

### 7.4 Разбор значений

- Числа из XLSX — через `Decimal(str(value))`, не через арифметику float.
- Убрать пробелы, неразрывные пробелы, «₸», «тг»; одиночная запятая — десятичный разделитель.
- Больше 2 знаков после запятой, отрицательные и пустые обязательные значения — ошибка строки.
- Артикул — текст. Числовая ячейка без «.0». Вид `4,6E+12` — ошибка «Артикул испорчен Excel: задайте колонке текстовый формат».
- Если артикул не найден, но совпадает после добавления или удаления ведущих нулей — предупреждение с подсказкой, без молчаливого сопоставления.
- Ячейка-формула без сохранённого значения — ошибка «Пересохраните файл в Excel».
- Дубли артикула: по умолчанию не импортировать, показать и дать выбрать «последнее значение».

### 7.5 Дата начала действия

- У товара нет затрат и дата не указана → вопрос «Применить ко всей истории?» (по умолчанию «да»).
- Затраты уже есть и дата не указана → новая версия действует с момента загрузки; прошлые продажи не меняются.
- Дата указана → версия действует с этой даты; проверка показывает, сколько продаж пересчитается.

### 7.6 Применение и отмена

- До подтверждения данные не меняются. Валидные строки применяются одной транзакцией.
- Сохраняется запись о загрузке (имя файла, время, число строк, итог) без содержимого.
- Последнюю загрузку можно отменить, пока не применена следующая: её версии затрат помечаются отменёнными.
- Файл ошибок: при выгрузке текстовые ячейки, начинающиеся с `=`, `+`, `-`, `@`, табуляции или перевода строки, экранируются.

### 7.7 Комиссии

- Ставка категории: значение в bp, даты действия, источник, дата проверки, флаги «проверено» и «демо».
- Непроверенные ставки не подставляются по умолчанию; продавец вводит свою, расчёт помечается «оценка».
- Применяется ставка, действовавшая на дату выдачи заказа.

## 8. ИИ-помощник

### 8.1 Согласие

- До первого вопроса — экран согласия (`docs/design.md`, 12.13): что передаётся внешнему ИИ-сервису (сводные цифры, названия товаров, текст вопроса), что не передаётся (данные покупателей), как отозвать.
- Без согласия ни один запрос к ИИ-сервису не отправляется; помощник недоступен, остальное работает.
- Согласие хранится на сервере с датой и версией текста; отзыв — в профиле.

### 8.2 Поток запроса

1. Сервер проверяет вопрос (длина до 500 символов, лимит, согласие).
2. Модель выбирает разрешённые read-only инструменты — не больше 3 вызовов.
3. Сервер выполняет инструменты по данным магазина пользователя и сохраняет результат в `ReportSnapshot`.
4. Результат превращается в список фактов с id (`F1`, `F2`, …), типом и ссылкой на snapshot.
5. Модель возвращает **шаблон ответа без цифр** с плейсхолдерами: «Прибыль снизилась на {F3} ({F4}). Главная причина — {F7}: продажи упали с {F8} до {F9}.»
6. Проверка: в шаблоне нет цифр; все плейсхолдеры существуют; названия товаров — только плейсхолдерами. При нарушении — одна повторная попытка, затем безопасный ответ, собранный сервером из фактов.
7. Сервер подставляет значения с форматированием и собирает `evidence`, `missingData`, `confidence`.

### 8.3 Инструменты

- `get_sales_summary(period)`
- `get_profit_summary(period, include_estimates)`
- `get_top_products(period, metric, order, limit)` — `metric`: `profit` | `revenue` | `qty`; `order`: `desc` | `asc`; `limit` ≤ 20
- `get_product_profit(product_id, period)`
- `get_missing_costs()`
- `compare_periods(period_a, period_b)`
- `explain_profit_change(period_a, period_b)`
- `get_return_cancel_summary(period)`

Период — пресет (`today`, `yesterday`, `last_7_days`, `last_14_days`, `last_30_days`, `last_90_days`, `this_month`, `previous_month`, `previous_equal_period`) или явные даты; пресеты в даты переводит сервер по часовому поясу магазина. Аргументы проверяются схемами; доступ — до вызова. Инструментов, которые что-то меняют или отправляют, нет.

### 8.4 `explain_profit_change`

Для каждого товара сопоставимого набора: `q` — единиц в завершённых продажах, `u` — средняя прибыль на единицу до возвратов, `R` — потери от возвратов, `P = q × u − R`.

```text
эффект объёма          = (q_B − q_A) × u_A
эффект юнит-экономики  = (u_B − u_A) × q_B   (раскладывается на цену, себестоимость, комиссию, доставку)
эффект возвратов       = −(R_B − R_A)
```

Если `q_A = 0`, принимается `u_A = u_B`. Эффекты считаются точно (дробями), затем округляются до тиына; остаток — строкой «округление», сумма эффектов точно равна изменению прибыли. Результат: итоги периодов, изменение, товары по величине вклада, `top_driver` и его доля, покрытие обоих периодов, товары вне сопоставимого набора, изменение расходов магазина.

### 8.5 Ответ

```json
{
  "answerTemplate": "Прибыль снизилась на {F3} ({F4}). Главная причина — {F7}: продажи упали с {F8} до {F9}.",
  "renderedAnswer": "заполняет сервер",
  "period": {"from": "2026-11-06", "to": "2026-11-19"},
  "comparisonPeriod": {"from": "2026-10-23", "to": "2026-11-05"},
  "dataAsOf": "2026-11-19T10:40:00Z",
  "evidence": [{"factId": "F3", "label": "Изменение прибыли", "valueMinor": -4520000, "currency": "KZT", "snapshotId": "rs_000123"}],
  "missingData": ["У 10 из 40 товаров нет закупочной цены"],
  "suggestedActions": [{"type": "open_product", "entityId": "D007", "label": "Открыть товар"}],
  "confidence": "medium",
  "confidenceReason": "Покрытие 88,9% чистых продаж"
}
```

Модель заполняет только `answerTemplate` и `suggestedActions` (тип — из разрешённого списка, `entityId` — только из результатов инструментов). Остальное формирует сервер.

**Уверенность (считает сервер):** `high` — покрытие ≥ 95% во всех периодах, нет оценок, данные свежие (в демо — всегда; с Kaspi — синхронизация не старше 24 часов); `medium` — покрытие 70–95% или есть оценки; `low` — покрытие < 70%, устаревшие данные или частичные ошибки. Если данных недостаточно — список недостающего вместо уверенности.

### 8.7 Провайдер и лимиты

- Интерфейс `AIProvider`; `MockProvider` по умолчанию в разработке и тестах.
- Живая модель на синтетических данных — с ключом только на сервере и дневным бюджетом; для показа продавцам — не меньше 90% автоматических проверок eval.
- Живая модель на реальных данных — после выбора поставщика, проверки региона и сроков хранения, договора и юридического согласования.
- Лимиты: вопросов в день на пользователя (по умолчанию 20), максимум токенов, таймаут 30 секунд, один повтор при временной ошибке, отключение при исчерпании бюджета.
- Учёт: модель, токены, оценка стоимости, id запроса — без текста вопроса.

### 8.8 Безопасность ответов

- Результаты инструментов передаются модели как данные с пометкой, что это не инструкции; названия товаров обрезаются по длине и попадают в ответ только через плейсхолдеры.
- Приложение показывает ответ как обычный текст; ссылки и разметка из ответа модели не исполняются.
- Жалоба на ответ (`flag`) доступна у каждого ответа и черновика; жалобы сохраняются и просматриваются.
- Тест инъекции — вопрос 11 eval-набора.

### 8.9 Черновики

- Описание товара строится только по введённым фактам и фото; неизвестные характеристики помечаются «Уточнить»; никаких выдуманных гарантий, брендов, материалов, совместимости, сертификатов, медицинских свойств.
- Числа в черновике допустимы, только если они есть во введённых фактах — сервер сверяет.
- Казахские тексты проверяет носитель языка на 20–30 примерах до бета-теста.
- Ответ покупателю — только из вручную вставленного вопроса; приложение ничего не отправляет.
- Фото удаляются с сервера после генерации; в ИИ-сервис не передаются данные покупателей.

## 10. Модель данных

Все даты — UTC с часовым поясом; периоды — в часовом поясе магазина (по умолчанию `Asia/Almaty`, UTC+5).

- `User`: email, имя, язык, создан, удалён.
- `AuthCode`: хеш кода, email, срок, попытки.
- `Session`: пользователь или демо-установка, хеш токена обновления, устройство, срок, отозвана.
- `DemoInstallation`: id установки (хеш), песочница, последняя активность.
- `Workspace`, `Membership` (роль владельца), `Shop`, `Category`, `Product`.
- `ProductCostVersion`: закупка, доставка до склада, упаковка, прочее (тиыны на единицу), `effective_from` (пусто — с начала истории), источник, загрузка, отменена.
- `CommissionPreset`: категория, ставка bp, даты, источник, проверено, демо, кем создано.
- `Order`, `OrderItem` (цена, количество, доставка покупателю и её источник), `ReturnEvent` (компоненты возврата, каждый может быть неизвестен).
- `ExpenseEntry`: тип, сумма, период, источник.
- `ImportBatch`, `ImportRowError`, `ImportMapping` (запомненное сопоставление колонок).
- `ReportSnapshot`.
- `AIConsent` (версия текста, дата, отозвано), `AIConversation`, `AITurn` (шаблон, ответ, инструменты, факты, уверенность), `AIFeedback` (оценка, причина жалобы, комментарий), `AIUsageEvent`.
- `ProductDraft`, `ReplyDraft`.
- `AuditEvent`: действие, сущность, результат, время — без токенов и персональных данных.

## 11. Интеграция Kaspi — этап B, за флагом

- Известно из документации Kaspi: API продавца работает по ключу (токену) из кабинета; описаны получение заказов и переходы статусов; цены и остатки — через кабинет, прайс-лист или XML, XML проверяется примерно раз в 60 минут; прайс-лист скачивается в Excel.
- Наблюдения интегратора SelSup (проверить): полный каталог через API не передаётся (связывают через Excel); загружаются FBS-заказы, FBO — нет; токен формирует только руководитель компании.
- Не подтверждено: цены и продажи конкурентов, чат с покупателями, рекламные ставки, webhooks, «реальное время».
- Правила: только чтение заказов по документированным методам; ключ хранится на сервере зашифрованным и никогда не возвращается в приложение; никаких логинов и паролей Kaspi, скрейпинга и неофициальных методов; синхронизация показывает время и ошибки; ИИ ничего не меняет в Kaspi.
- До письменных ответов на вопросы `docs/owner.md` — только mock и выключенный флаг.

## 12. Требования App Store и Google Play

### 12.1 Общие

- iPhone и Android-телефоны, только портрет; iPad в первой версии не поддерживается.
- Политика конфиденциальности и условия использования — по постоянным HTTPS-ссылкам, доступны в приложении и в карточке магазина.
- Удаление аккаунта внутри приложения (`docs/design.md`, 12.22) и веб-страница для запроса удаления.
- Демо-режим и аккаунт проверяющего с инструкцией — чтобы проверяющие могли открыть все функции.
- Название, иконка, скриншоты и ключевые слова — без товарного знака и цветов Kaspi без письменного разрешения; в приложении упоминание Kaspi — только по смыслу («Подключение Kaspi») и строка «Satti Seller — независимый сервис, не связан с Kaspi.kz».
- Разрешения — только нужные: камера и выбор фото (черновик карточки), позже — уведомления. Тексты запросов разрешений — на русском и казахском, с понятной причиной. Запрос — в момент действия, не при запуске.
- Никаких рекламных и трекинговых SDK; запрос на отслеживание (App Tracking Transparency) не нужен.
- Подписки и платные функции (этап D) — только через покупки в приложении App Store и Google Play Billing, если правила на момент запуска не позволяют иного.

### 12.2 Apple

- С 28 апреля 2026 года сборки для App Store Connect должны собираться в Xcode 26 или новее с SDK iOS 26 или новее. Использовать актуальный Expo SDK и образы сборки EAS; следить за следующими требованиями Apple.
- Вход только по email-коду: дополнительный вход через Apple не требуется. Если позже добавится вход через Google или другой сторонний сервис, нужно добавить равноценный вариант с защитой приватности, например «Войти с Apple».
- Передача персональных данных внешнему ИИ-сервису — только после явного согласия пользователя внутри приложения и с раскрытием, куда уходят данные (раздел 8.1). Политика конфиденциальности должна это описывать.
- Демо- и бета-версии — только через TestFlight; в App Store — полноценная версия (раздел 2).
- Метка конфиденциальности в App Store Connect: email, содержимое пользователя (импортированные затраты, вопросы помощнику, фото для черновиков), данные использования и диагностика — «для работы приложения», не для отслеживания.
- Шифрование: только стандартный HTTPS — указать это в настройках сборки, чтобы не заполнять экспортную форму при каждой загрузке.
- Ответы на обновлённую анкету возрастного рейтинга.

### 12.3 Google Play

- С 31 августа 2026 года новые приложения и обновления должны быть нацелены на Android 16 (API 36) или выше.
- Edge-to-edge и учёт безопасных зон обязательны.
- Новый личный аккаунт разработчика (созданный после 13 ноября 2023 года) должен провести закрытый тест: не меньше 12 тестировщиков, подключённых без перерыва 14 дней, прежде чем можно запросить публикацию. Аккаунт организации, по описаниям сторонних источников, от этого освобождён — проверить при регистрации.
- Приложения, которые генерируют контент с помощью ИИ, должны давать пожаловаться на оскорбительный контент прямо в приложении — кнопка «Пожаловаться» у ответов и черновиков.
- Форма «Безопасность данных»: те же данные, что в метке Apple; данные шифруются при передаче; пользователь может запросить удаление.
- Для фото — системный выбор фото без широкого доступа к галерее.
- Анкета возрастного рейтинга (IARC).

## 13. Безопасность и приватность

- Токены сессии — только в Keychain / Keystore; не в обычном хранилище, логах и отчётах об ошибках.
- Кэш данных магазина на телефоне — без данных покупателей; очищается при выходе и удалении аккаунта.
- В приложении нет секретов: ключи ИИ-сервиса, Kaspi и почты — только на сервере.
- Только HTTPS; сервер не отдаёт stacktrace.
- Логи сервера — без токенов, кодов входа, email (только хеш), содержимого файлов и ответов ИИ.
- Реальные данные — только на этапах B–D и только в инфраструктуре с размещением в Казахстане (БД, резервные копии, файлы, логи).
- Карта данных `docs/data-map.md`: какие данные, где, кто обрабатывает (хостинг, почта, ИИ-сервис, мониторинг), сколько хранится. Обновляется при каждом новом обработчике.
- Экспорт данных пользователя — на этапе B; удаление — с этапа A для аккаунтов.

## 14. Аналитика и ошибки

- События — на своём сервере, без сторонних SDK: `demo_started`, `signup_completed`, `overview_opened`, `period_changed`, `product_opened`, `cost_quick_entry_saved`, `import_started`, `import_applied`, `import_undone`, `ai_consent_given`, `ai_question_sent`, `ai_answer_failed`, `ai_answer_reported`, `draft_created`, `draft_copied`, `account_deleted`.
- В событиях нет текста вопросов, email, названий файлов и сумм конкретных заказов.
- Сбор отчётов об ошибках (например, Sentry) — в тестовых сборках с вырезанием персональных данных; в публичной версии — после решения юриста и с отражением в метке конфиденциальности.
- Пользователь видит код ошибки, а не технические подробности.

## 15. Качество

- **Сервер:** golden G001–G008, агрегат, R001–R003; импорт (набор тестовых файлов: cp1251, точка с запятой, потерянные нули, `4,6E+12`, дробные из XLSX, формула без значения, дубли, превышение размера); отчёты и `explain_profit_change` (сумма эффектов = изменению); eval помощника; доступ только к своему магазину.
- **Приложение:** тесты форматирования (ru, kk, отрицательные, большие суммы, даты); тесты компонентов; сквозные проверки основных сценариев: демо → обзор → товар → изменить затраты; импорт файла; вопрос помощнику; вход и удаление аккаунта.
- **Устройства:** iPhone SE, обычный iPhone, iPhone Pro Max; Android среднего уровня (около 4 ГБ памяти) и современный Android; светлая и тёмная тема; крупный шрифт; русский и казахский.
- **Скорость:** холодный запуск до 3 секунд на Android среднего уровня; плавная прокрутка списка из 500 товаров; экраны с кэшем открываются без ожидания.
- **Доступность:** чек-лист `docs/design.md`, раздел 13.
