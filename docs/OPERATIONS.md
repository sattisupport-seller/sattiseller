# Эксплуатация: бэкапы, восстановление, ключи

Документ для владельца. Решения — `docs/adr/0005-launch-decisions.md`.

## Что копируется

- База данных: `pg_dump` (PostgreSQL) или копия файла через API SQLite (только для разработки).
- Файл `secret_key` из папки данных (`SATTI_DATA_DIR`). Без него сессии и хеши пробного периода не совпадут.
- Копии шифруются ключом `SATTI_BACKUP_KEY`. Без ключа бэкап не создаётся.

Не копируется: `.env` и значение `SATTI_TOTP_KEY` — их храните отдельно (см. ниже).

## Расписание и хранение

- Ежедневно (cron на сервере): `cd /opt/satti/server && python scripts/backup.py create`.
- Локально — `SATTI_BACKUP_DIR` (по умолчанию `server/backups`), хранение `SATTI_BACKUP_KEEP_DAYS` (14).
- Во второе хранилище — если задано `SATTI_S3_BUCKET`: выгрузка в `satti/`, объекты старше 14 дней удаляются.

## Восстановление

1. Поднять чистую базу (`DATABASE_URL` на новую базу).
2. `python scripts/backup.py restore <файл.bak> --target-url <URL новой базы>`
3. Боевая база восстанавливается только с флагом `--yes`, и только намеренно.
4. Сверить число магазинов и заказов с отчётом о последней копии.

Учения (2026-11-20, локально, PostgreSQL 16, 65 400 заказов): создание 3 с, копия 9,6 МБ, восстановление 5 с, числа строк совпали (218 магазинов, 65 400 заказов). Учения на сервере — при первом развёртывании.

## Ключи — как хранить (инструкция владельцу)

- `SATTI_BACKUP_KEY` — создаётся командой `python scripts/backup.py genkey`. Сохраните в менеджере паролей. Потеряете — копии не расшифруются.
- `secret_key` (файл в папке данных) — сохраните копию в менеджере паролей (как файл) и в защищённом хранилище. Не присылайте в чат и не кладите в git.
- `SATTI_TOTP_KEY` и `SATTI_BILLING_PEPPER` — отдельно от бэкапов. Если их потерять, 2FA администратора придётся настроить заново, а хеши пробного периода перестанут сходиться.
- Ключи S3 — только в `.env` сервера.

## Откат миграций

`alembic downgrade` ниже текущей версии удаляет данные. Перед откатом — копия (`backup.py create`).

## Ежедневные проверки (4.8)

Каждый день (владелец или дежурный, 5 минут):
1. `GET /v1/health` отвечает 200; в журнале (SATTI_LOG_FILE) нет всплеска ошибок 5xx.
2. Последний бэкап создан за сутки (папка SATTI_BACKUP_DIR, файл с сегодняшней датой), размер не нулевой.
3. Оповещения владельцу (письма 3.10) пришли; если есть письмо о всплеске ошибок — открыть журнал ошибок в админ-панели.
4. Бюджет ИИ не превышен (админ-панель, блок «Бюджет»); если выключатель помощника включён — проверить расход за сутки.

## Журнал сервера (4.2)

- Файл журнала задаётся SATTI_LOG_FILE; размер одного файла — SATTI_LOG_MAX_MB (по умолчанию 10 МБ), число старых копий — SATTI_LOG_BACKUPS (по умолчанию 5). Старые копии удаляются автоматически при ротации.
- В журнал не пишутся ключи, пароли, коды входа и тела запросов. Тексты вопросов к помощнику в журнал не попадают.

## Сбой

1. Сервис недоступен: проверить `/v1/health`, журнал и место на диске; перезапуск процесса.
2. Ошибки базы: остановить приём запросов (maintenance_message в конфиге приложения), проверить соединение с PostgreSQL, восстановить из последнего бэкапа при порче данных (раздел «Восстановление»).
3. Ошибки ИИ-провайдера: помощник отвечает честным сообщением «не удалось проверить»; при длительном сбое выключить флаг ai_assistant в админ-панели.

## Ротация ключей

- Ключ Anthropic (ANTHROPIC_API_KEY), ключ сессий (secret_key), SATTI_BILLING_PEPPER, SATTI_TOTP_KEY, SATTI_BACKUP_KEY — меняются по плану и при подозрении на утечку. Смена ключа сессий выходит всех из входа; смена ключа шифрования требует перешифрования (инструкция — перед сменой).
- Порядок: создать новый ключ → обновить .env → перезапуск → проверить вход и бэкап → записать дату в журнал владельца.

## Утечка персональных данных (шаблон для владельца)

Если есть подозрение, что персональные данные покупателей или продавцов попали к посторонним:
1. В течение часа: закрыть доступ (сменить ключи, отключить внешние интеграции), сохранить журнал.
2. В течение 1 рабочего дня: уведомить уполномоченный орган о факте утечки (состав данных, число людей, меры). Текст уведомления — по форме уполномоченного органа; юрист проверяет до отправки.
3. Уведомить пользователей, если утечка создаёт риск для них (текст согласовать с юристом; см. OWNER_TODO).

## Учения восстановления (22.11.2026, локальный PostgreSQL)

Что сделано: демо-магазин (2 магазина, 80 товаров, 600 заказов, 880 позиций, 60 версий затрат, 30 возвратов, 4 расхода) → `scripts/backup.py create` (шифрование, дамп PostgreSQL) → `scripts/backup.py restore` в отдельную базу `satti_restore` → сверка.

Результат: совпадают все проверенные таблицы, число заказов по статусам (cancelled 50, completed 440, in_progress 40, partial_return 6, pending 40, returned 24) и сумма позиций (563 544 000 тиын). Расхождений нет.

Что важно знать:
- Ключ `SATTI_BACKUP_KEY` нужен и для создания, и для восстановления. Без него копию не открыть: хранить ключ отдельно от копии (см. пункт 16 в `OWNER_TODO.md`).
- Утилиты `pg_dump` и `pg_restore` берутся через `SATTI_PG_BIN` или из PATH.
- Учения на реальном сервере и с реальными данными — после развёртывания (пункт 4.7).

## Развёртывание (Ubuntu 24.04, Docker Compose) — файлы в deploy/ и server/Dockerfile

Состав: `db` (PostgreSQL 16, healthcheck), `app` (сервер Satti, healthcheck на `/v1/health`, перезапуск), `caddy` (HTTPS, заголовки безопасности, лимит тела запроса 10 МБ).

Первый запуск:
1. Установить Docker Engine и плагин compose v2.
2. `cp deploy/.env.example deploy/.env`, заполнить, `chmod 600 deploy/.env`. Ключ `SATTI_BACKUP_KEY` сохранить отдельно от сервера.
3. Направить A-запись домена на сервер; порты 80 и 443 открыть.
4. `./deploy/deploy.sh up`.

Обновление: тот же `./deploy/deploy.sh up`. Скрипт делает бэкап, собирает образ, применяет миграции, перезапускает и проверяет `/v1/health`. Если проверка не прошла — сам вызывает откат.

Откат: `./deploy/deploy.sh rollback`. Откатывает последнюю миграцию (через `SATTI_ALLOW_DOWNGRADE=1` — откат миграции удаляет данные этой миграции, поэтому перед ним делается бэкап) и возвращает предыдущий образ.

Что проверено и что нет:
- Проверено: синтаксис `deploy.sh` (`bash -n`), структура `docker-compose.yml` (YAML, три сервиса, healthcheck у каждого), наличие файлов, которые копирует Dockerfile.
- Не проверено: сборка образа и запуск — Docker на машине разработки не установлен. Первый реальный запуск — на сервере; при сбое см. раздел «Учения восстановления» и план отката.
- Caddy в compose ссылается на `SATTI_DOMAIN`; выпуск сертификата требует открытых 80 и 443 и настроенной A-записи.
