## 2. Качество исходного кода

### 2.1 Что сделано профессионально

- **Проверка владения данными.** Все маршруты `/v1/shops/{id}/...` начинаются с `shop_for`. Для объектов внутри магазина (заказы, товары, версии затрат, расходы, импорт, диалоги ИИ) есть явная проверка `obj.shop_id == shop.id`. В прогоне ниже 13 маршрутов на чужом магазине вернули 403 или 404 (тесты `test_qa_security.py`).
- **Токены и коды хранятся только в виде хешей** (HMAC-SHA256 с ключом сервера). Refresh-токен ротируется; повторное использование старого даёт 401 (проверено, см. раздел 4).
- **Деньги в `Decimal`**, суммы в тиынах, без `float` (`money.py`, `exports.py`).
- **Экспорт CSV экранирует формулы** (`csv_safe`), XLSX-экспорт пишет значения, а не формулы.
- **Проверка конфигурации при старте** в продакшене (`production_config_problems`) — правильная идея, но список неполный (AUD-10).
- **Ошибки API** в едином формате с кодом, локализованным сообщением (ru / kk) и `error_id`, без трассировки в ответе (проверено: 404 без «Traceback»).
- **Маскировка персональных данных** для ИИ (телефоны, email, адреса, словарь покупателей) и в журнале ошибок.
- **Секреты не в git:** `.gitignore` закрывает `server/data/`, `*.db`, `.env`, `secrets/`. Поиск по шаблонам ключей и паролей в tracked-файлах ничего не нашёл.
- **Мобильное хранилище** — `expo-secure-store` на телефоне; `localStorage` только в веб-просмотре.
- **Согласие на ИИ** проверяется во всех трёх маршрутах, которые передают данные модели.
- **Миграции Alembic линейны**, одна голова, подъём с пустой базы и откат до начального состояния проходят (проверено).

### 2.3 Потенциальные конфликты и гонки

- **Пробный период** (AUD-16): `BillingMark.key_hash` индексирован, но не уникален; два параллельных запроса на пробный период могут оба пройти проверку `trial_eligible`.
- **Лимит ИИ** (AUD-17): проверка количества и вставка события — два шага без блокировки; при параллельных запросах возможно небольшое превышение 30 в сутки.
- **Планировщик хранения:** если `SATTI_SCHEDULER=1` запущен в нескольких процессах, письма о хранении могут уйти дважды. Таблица `retention_events` защищает только последовательные запуски.
- **Асинхронность импорта** (AUD-06): обработчик `import_upload` объявлен `async`, но внутри синхронно вызывает `parse_file`. Пока файл разбирается, цикл событий занят, и остальные запросы сервера ждут.
- **Утечек памяти по коду не найдено.** Потоки планировщика и кэш JWKS ограничены по времени (кэш на час).

### 2.4 Масштабирование

- Все расчёты пересчитываются на каждый запрос из всех заказов магазина (O1 из QA, подтверждено нагрузкой, раздел 7).
- Лимиты запросов и кэш ключей провайдеров — в памяти одного процесса. При нескольких процессах или серверах лимиты не работают (AUD-14).
- SQLite по умолчанию. Для нескольких процессов и реальной нагрузки нужна PostgreSQL. Код в основном совместим с ORM, но миграции и тесты проверены только на SQLite.

- **Вход через Apple и Google** с реальными ключами не проверен: нет аккаунтов разработчика. Проверена только логика на тестовых ключах (QA, O6).

- **Покупки App Store и Google Play** не проверены: проверка покупок не реализована (AUD-03).
- **Одновременная работа нескольких пользователей** — только нагрузка на чтение (раздел 7); гонки на записи проверены чтением кода, не воспроизводились.
- **Потеря соединения, повторное нажатие кнопок** в приложении не проверялись на устройстве. По коду: повтор запросов в `rawRequest` есть только для запросов, помеченных `retryable`; ни один вызов в приложении такой флаг не ставит, поэтому повтора POST нет.

### 4.2 Проблемы

**AUD-11 (HIGH). Alembic не знает о части таблиц.** `server/migrations/env.py` импортирует только `app.models`. Таблицы `subscriptions`, `billing_marks`, `retention_events`, `admin_totp`, `feature_flags` описаны в `billing.py` и `admin.py` и в `target_metadata` не попадают.

- Опасность: при `alembic revision --autogenerate` будет сгенерирована миграция на удаление этих таблиц. Применённая по ошибке, она уничтожит данные подписок и отметок защиты пробного периода.
- Исправление: импортировать `app.billing`, `app.admin`, `app.social_auth`, `app.errorlog` в `env.py`.
- Проверка: `alembic check` проходит без расхождений.

**AUD-13 (HIGH). Нет резервного копирования и восстановления.** В репозитории нет скриптов, расписания и процедуры восстановления. Документы упоминают копии, но инструментов нет. Отдельно: `data/secret_key` хранит ключ всех хешей. Если файл потерян, все сессии становятся недействительными, а отметки пробного периода перестают сравниваться (пользователи смогут взять пробный период повторно).
- Исправление: регулярный бэкап `satti.db` и `secret_key` (вне сервера), проверенная процедура восстановления на тестовой среде, резервная копия ключа в защищённом хранилище.
- Проверка: восстановление из копии на отдельной машине, затем сверка количеств строк и вход в аккаунт.

**Целостность данных.** Удаление магазина каскадно удаляет все дочерние записи (ОК). Удаление аккаунта оставляет часть данных (AUD-08).

## 5. Безопасность

### 5.1 Что проверено и не найдено

- **SQL-инъекции:** SQL-строк с пользовательскими значениями нет. Все запросы через ORM (`select`, `delete`, `scalar`). Вызовов `text()` и `execute()` с форматированием строк нет. Тесты на SQL-подобный ввод — в `test_qa_security.py`.
- **XSS:** API возвращает JSON. Админ-панель (`admin.html`) экранирует все значения через `esc()` (проверено по коду: `&`, `<`, `>`, `"`, `'`). Юридические страницы собраны из собственных файлов репозитория через markdown; пользовательский ввод туда не попадает. Мобильное приложение не использует `WebView` и `dangerouslySetInnerHTML`.
- **Права доступа:** проверено по коду на всех маршрутах (раздел 2.1) и тестами.
- **Хранение паролей:** паролей нет. Вход по коду и через провайдеров. Коды и токены — HMAC с секретом сервера.
- **Токены:** access 15 минут, refresh 30 дней с ротацией, logout отзывает сессию (проверено: после logout access и refresh дают 401).
- **Вход через Apple/Google:** подпись RS256 по JWKS провайдера, издатель, аудитория, срок, nonce (`social_auth.py`). Логика корректна; с реальными ключами не проверена.
- **Заголовки безопасности и CSP:** есть (проверено).
- **Админ-панель:** для всех, кроме владельца, маршруты дают 404. Доступ по TOTP в заголовке.
- **Секреты в git:** не найдены.
- **Загрузка файлов:** лимит 5 МБ, лимит распаковки 50 МБ, лимит строк 5000, отказ от `.xls`/`.xlsm`.

### 5.2 Найденные проблемы безопасности и устойчивости

**AUD-04 (HIGH). Выход из аккаунта при параллельном обновлении токена (мобильное приложение).**
- Где: `mobile/src/api/client.ts`, функция `request` и `refreshTokens`.
- Проблема: при истечении access-токена каждый запрос, получивший 401, сам вызывает `refreshTokens()`. Общей блокировки нет. Сервер при ротации отзывает старый refresh. Первый запрос обновляет токен, второй отправляет тот же старый refresh и получает 401. Тогда `refreshTokens` возвращает `false`, вызывается `clearSession()` и `onSessionLost()` — пользователь выходит из аккаунта.
- Как воспроизвести: открыть экран, который делает несколько запросов сразу (обзор, заказы, товары), подождать истечения access-токена (15 мин) и открыть его. Серверная часть воспроизведена: два обновления подряд с одним refresh дают 200 и 401 (`audit_probe.py`, шаг «old refresh reused → 401»). Полный сценарий в приложении не воспроизводился.
- Опасность: регулярный выход пользователей из аккаунта; потеря черновиков и несохранённых данных.
- Исправление: единая «одиночная» операция обновления — все параллельные вызовы ждут один и тот же промис. Дополнительно сервер может выдавать короткое окно (например, 30 с), в котором повторный refresh с тем же токеном возвращает уже выданные токены.
- Проверка: юнит-тест на клиенте с двумя параллельными запросами, которые получают 401; в сценарии на устройстве — выход через 15 минут не происходит.

**AUD-05 (HIGH). Демо-сессии без ограничения, неаутентифицированный рост базы.**
- Где: `api.py: demo_session` (`POST /v1/demo/session`), `X-Device-Id` не проверяется и не ограничивается.
- Измерение: 25 новых устройств подряд — все 200, в среднем 761 мс на сессию (`audit_probe.py`). База после 27 демо-сессий — 7,1 МБ, что по оценке даёт около 260 КБ на демо-магазин (базовый размер базы учтён не был).
- Опасность: любой клиент без входа создаёт магазин с 300 заказами за 90 дней. Миллион запросов — около 260 ГБ данных и около 9 суток работы одного ядра процессора (761 мс на сессию). Очистка только через 30 дней бездействия (`demo_idle_days`).
- Исправление: лимит на IP и на устройство (как для входа), ограничение общего числа демо-магазинов, очистка по времени создания без активности, отказ при превышении.
- Проверка: 50 запросов с разных `X-Device-Id` с одного IP — после лимита 429; размер базы растёт не быстрее лимита.

**AUD-06 (HIGH). Импорт большого файла блокирует сервер.**
- Где: `api.py: import_upload` (`async def`, внутри синхронный `parse_file`); `imports.py: _parse_xlsx`.
- Измерение: XLSX на 200 000 строк, 2,7 МБ (проходит лимит 5 МБ) — ответ 400 через 45 секунд (`audit_probe.py`). Ошибка «больше 5000 строк» возникает только после того, как вся таблица загружена в память (`list(ws.iter_rows(...))`), и книга открывается дважды.
- Опасность: один запрос занимает процессор на 45 секунд. Поскольку обработчик `async`, синхронный разбор занимает цикл событий, и все запросы сервера ждут. Это отказ в обслуживании одним аккаунтом. По коду; отдельно от запросов других пользователей не измерялось.
- Исправление: отказывать по числу строк во время потокового чтения (`iter_rows` с остановкой на 5001); открывать книгу один раз; вынести разбор в пул потоков (`run_in_threadpool`) или фоновую задачу; ограничивать размер распакованного XML потоково.
- Проверка: тот же файл — отказ за секунды; параллельный запрос `GET /v1/health` во время разбора отвечает без задержки.

**AUD-07 (HIGH). Лимит импорта обходится обновлением токена.**
- Где: `api.py: import_upload`, ключ `imp:{principal.session_id}`.
- Проблема: лимит 10 импортов в час привязан к сессии, а при каждом обновлении токена создаётся новая сессия с новым `session_id`.
- Измерение: без обновления — 10 успешных импортов и 2 отказа 429. С обновлением перед каждым — 12 из 12 успешных (`audit_ratelimit.py`).
- Опасность: лимит не работает; вместе с AUD-06 это простой способ загрузить сервер.
- Исправление: ключ лимита — идентификатор аккаунта или магазина, а не сессии.
- Проверка: тот же скрипт — 11-й импорт возвращает 429 независимо от обновлений токена.

**AUD-08 (HIGH). Удаление аккаунта не удаляет все персональные данные.**
- Где: `api.py: deletion_confirm` и `web.py: delete_user_account`.
- Измерение (`audit_deletion.py`): после удаления аккаунта остались
  - 2 строки `auth_codes` с открытым email (таблица хранит `email` без хеширования);
  - 1 строка `ai_usage_events` с `user_id` без владельца.
- Проверено по коду, не прогоном: строки `social_identities` (провайдер и subject Apple/Google) не удаляются, таблица без внешнего ключа на `users`.
- Опасность: нарушение обещания «данные удаляются» (ТЗ 2.1, раздел 10, и политика конфиденциальности); при повторном входе через Google или Apple старый subject снова связывается с новым аккаунтом.
- Исправление: в обеих функциях удалять `auth_codes` по email и user_id, `social_identities` по user_id, `ai_usage_events` по user_id; вынести одну функцию удаления и использовать в обоих местах.
- Проверка: тот же скрипт — все счётчики 0; новый тест в `tests/`.

**AUD-09 (HIGH). Известные уязвимости зависимостей.**
- Сервер (`pip-audit`, 52 advisories):

| Пакет | Версия | Advisories | Исправлено в |
|---|---|---|---|
| pyjwt | 2.10.1 | 22 | 2.12.0+ |
| starlette | 0.41.3 (через fastapi 0.115.6) | 14 | 0.47.2+ / 1.0.1 |
| python-multipart | 0.0.20 | 12 | 0.0.22+ |
| markdown | 3.7 | 2 | 3.8.1 |
| pytest | 8.3.4 | 2 | 9.0.3 (только тесты) |

- Приложение (`npm audit --omit=dev`): 20 moderate, в основном через `expo` и `@expo/fingerprint`; в полном дереве 22 moderate (`jest`, `babel-jest` и др. — только для разработки).
- Применимость к нашему коду **не проверялась** для каждого advisory. Наиболее важные для нас: `pyjwt` (проверка токенов входа), `python-multipart` (загрузка файлов) и `starlette` (весь API). Высокий приоритет — обновить эти три.
- Исправление: обновить `pyjwt`, `python-multipart`, `starlette` (через обновление `fastapi`), `markdown`, `pytest` и прогнать тесты; обновить зависимости приложения, где это возможно, с проверкой сборок.
- Проверка: `pip-audit -r requirements.txt` и `npm audit --omit=dev` без advisories высокого и критического уровня; все тесты проходят.

**AUD-10 (HIGH). Проверка конфигурации продакшена неполная.**
- Где: `config.py: production_config_problems`. Проверяются только 4 параметра: `BILLING_PEPPER`, `TOTP_KEY`, CORS и `EMAIL_LOGIN`.
- Не проверяются:
  - `SATTI_BILLING_ENFORCED` (по умолчанию `0`). Без него блокировки по подписке нет: все магазины работают бесплатно.
  - `SATTI_BILLING_TEST_MODE`. При `1` пробный период выдаётся без магазина приложений (`store="test"`).
  - `SATTI_SCHEDULER` (по умолчанию `0`). Без него удаление данных по хранению (90 дней) никогда не запускается, и это нарушает обещание ТЗ 2.1, раздел 9.3.
  - `SATTI_ADMIN_EMAIL` (пусто — панель закрыта; это безопасно, но не проверяется).
  - `SATTI_GOOGLE_CLIENT_IDS` (пусто — вход через Google даёт 503).
- Исправление: добавить проверки для каждого пункта: при `SATTI_ENV=production` `BILLING_ENFORCED=1`, `BILLING_TEST_MODE=0`, `SCHEDULER=1`, `ADMIN_EMAIL` задан, `GOOGLE_CLIENT_IDS` задан, либо явно сказано, какой способ входа включён.
- Проверка: тесты `production_config_problems` для каждой комбинации; запуск `SATTI_ENV=production` с неполной конфигурацией отказывает.

**AUD-14 (MEDIUM). Лимиты запросов по IP не работают за прокси.**
- Где: `ratelimit.py` (в памяти процесса), `request.client.host` в `auth_email_start`, `errorlog.py`. В коде нет обработки `X-Forwarded-For` и настроек доверенных прокси.
- Опасность: за обратным прокси (типичный продакшен) все клиенты имеют один IP. Тогда лимит кодов входа (20 в час на IP) становится общим лимитом для всех пользователей. Одновременно лимит не работает при нескольких процессах: каждый процесс считает отдельно.
- Исправление: доверенный прокси и разбор `X-Forwarded-For` (с ограничением доверенного адреса); общее хранилище лимитов (Redis или таблица в базе) при нескольких процессах.
- Проверка: два запроса с разными `X-Forwarded-For` через доверенный прокси считаются отдельно.

**AUD-15 (MEDIUM). Код 2FA администратора можно повторить в течение 90 секунд (O2, частично).**
- Где: `admin.py: totp_verify`, `require_admin`.
- Состояние: секрет зашифрован (исправлено в 308ff9c). Повтор кода не запрещён. Запрет повтора «одного кода — один раз» сломает веб-панель, которая шлёт код с каждым запросом.
- Исправление: обмен кода на сессионный токен админа на 15–30 минут; тогда повтор кода не нужен и запрет повтора безопасен.
- Проверка: после обмена повторная отправка того же кода даёт 401/403.

**AUD-18 (MEDIUM). Публичный сбор ошибок.**
- Где: `errorlog.py: POST /v1/telemetry/errors` — без входа, лимит 60 в час на IP (с проблемой AUD-14).
- Проблема: группы ошибок создаются по данным клиента (`kind`, `exc_type`, `where`). Один IP может создавать до 60 новых групп в час; при множестве IP таблица растёт без ограничения. Текст ошибки маскируется, но размер ограничен только по символам.
- Исправление: ограничить число групп (например, 500), при превышении писать в общий счётчик; проверять допустимые значения `kind` (перечень).
- Проверка: 1000 запросов с уникальными `where` — число групп не превышает лимита.

**AUD-16 (LOW–MEDIUM). Гонка при пробном периоде.** Индекс `billing_marks.key_hash` не уникален. Два параллельных запроса могут получить два пробных периода для одного аккаунта. Исправление: уникальный индекс `(kind, key_hash)` и обработка ошибки уникальности как 409. Проверка: два параллельных запроса дают один пробный период.

**AUD-17 (LOW). Превышение лимита ИИ при параллельных запросах.** Проверка количества и вставка события — два шага без блокировки. Исправление: блокировка строки магазина или атомарный счётчик. Проверка: 40 параллельных запросов дают не более 30 успешных.

**AUD-19 (LOW). Маскировка не покрывает ИИН и номера карт.** `privacy.py` маскирует телефоны, email, адреса и словарь покупателей. ИИН (12 цифр) и номера банковских карт не маскируются. Для ответов Kaspi это, вероятно, не нужно, но политика должна это фиксировать. Исправление: добавить шаблоны и тесты или явно записать в политике, что эти данные не передаются.

**AUD-23 (INFO). Привязка нового провайдера входа к аккаунту по email.** `social_auth.py: user_for_identity` связывает новый Apple или Google subject с существующим аккаунтом по подтверждённому email без дополнительного подтверждения. Риск ограничен, пока провайдер подтверждает владение email, но решение стоит зафиксировать в ADR.

**AUD-24 (INFO). Пробный период через второй email.** Принятое владельцем решение (ADR-0004): отметки аккаунта и магазина, без телефона. Обход возможен созданием второго аккаунта. Риск принят; записан здесь для полноты.

**AUD-25 (LOW). CSP админ-панели разрешает `unsafe-inline`.** Для страницы `/admin` это ослабляет защиту от XSS. Экранирование через `esc()` есть. Исправление: вынести скрипт в отдельный файл и убрать `unsafe-inline` из `script-src`.

### 6.2 Выводы

- **AUD-12 (HIGH). Пропускная способность не растёт с числом пользователей.** Около 8–9 запросов в секунду на всех уровнях нагрузки. Задержка растёт почти линейно: p95 1,6 с при 10 пользователях, 3,6 с при 20. Это подтверждает O1 из QA-отчёта: каждый запрос заново собирает все заказы магазина. С ростом магазина (тысячи заказов за период) задержка вырастет ещё сильнее.
- **Исправление:** кэш расчётов с инвалидацией при записи (заказы, затраты, налог) или агрегаты в базе. Перед этим — профилирование на данных размера реального магазина.
- **Проверка:** при 20 пользователях p95 ниже 500 мс на данных 10 000 заказов; повторный замер на одном и том же наборе.

**Чего не измерено:** длительный тест (час и больше), поведение при параллельной записи, нагрузка на сервер хостинга, время холодного старта приложения на телефоне, размер бандла (только факт сборки в QA).

## 9. Список найденных проблем

### CRITICAL — запуск недопустим

**AUD-01. Нет работающего входа в продакшене.**
- Где: `config.py` (`email_login_enabled` в продакшене должен быть 0), `social_auth.py` (`provider_not_configured` при пустом `SATTI_GOOGLE_CLIENT_IDS`), `main.py`.
- Проблема: при выключенном входе по коду и незаданных идентификаторах провайдеров вход в продакшене невозможен. Идентификаторы Apple и Google, ключи и аккаунты разработчика не настроены (задача 21).
- Воспроизведение: `SATTI_ENV=production`, `SATTI_EMAIL_LOGIN` не задан → `POST /v1/auth/email/start` → 404; `POST /v1/auth/google` без `SATTI_GOOGLE_CLIENT_IDS` → 503 (по коду; на сервере не запускалось).
- Опасность: ни один пользователь не войдёт.
- Исправление: настроить аккаунты, идентификаторы и ключи провайдеров; проверить вход с реальными токенами на тестовом устройстве.
- Проверка: вход через Apple и через Google на тестовом устройстве, выход, повторный вход, удаление аккаунта.

**AUD-02. Письма не отправляются пользователям.**
- Где: `mailer.py` — пишет `.eml` в папку `outbox`, отправки нет.
- Подтверждено: `audit_deletion.py` читает код удаления из `outbox`; ни одно письмо не уходит наружу.
- Опасность: коды входа по email и удаления аккаунта не доходят до пользователей; письма о хранении (ТЗ 2.1, 9.3) не отправляются.
- Исправление: подключить почтовый сервис (задача 23), обновить `mailer.py`, включить проверку в конфигурации (запуск отказывает без почтового ключа).
- Проверка: письмо с кодом приходит на реальный ящик тестировщика за 1 минуту.

**AUD-03. Оплаты нет.**
- Где: `billing.py: activate_paid` (нигде не вызывается), `api.py: post_verify_purchase` (всегда 501), `post_start_trial` (501 вне тестового режима).
- Подтверждено: `grep activate_paid` — только определение и `__all__`.
- Опасность: после пробного периода магазин нельзя оплатить. Если включить блокировку (`SATTI_BILLING_ENFORCED=1`), пользователи потеряют доступ навсегда. Без блокировки приложение бесплатное.
- Исправление: проверка покупок App Store Server API и Google Play Developer API, вызов `activate_paid` при успешной проверке, экраны оплаты в приложении (задачи 27, 19.3, 19.10).
- Проверка: покупка в Sandbox и тестовая дорожка Google Play — доступ открывается, отмена и возврат отражаются.

## 14. Финальная оценка

**Насколько качественно разработано приложение?** Хорошо для стадии демо. Архитектура понятная, проверки владения и хеширование токенов сделаны правильно, деньги посчитаны без ошибок округления. Но качество снижают неполное удаление данных, незакрытые лимиты, синхронный разбор файлов и отсутствие CI.

**Насколько правильно построена архитектура?** Разумно для одного сервера. Монолит `api.py`, лимиты в памяти, SQLite и почта в файлы ограничивают масштабирование. Переход на несколько процессов потребует общих лимитов и PostgreSQL.

**Насколько надёжно работает функционал?** Основные сценарии работают: 174 серверных теста и 19 тестов приложения проходят, исследовательский прогон API 23 из 23. Но есть ошибки, которые проявляются у реальных пользователей: выход при обновлении токена (AUD-04), обход лимитов (AUD-07), блокировка сервера на большом файле (AUD-06).

**Насколько безопасно приложение?** Основа безопасна: нет SQL-инъекций и XSS по найденным путям, токены хешируются, права проверяются. Слабые места: неполное удаление персональных данных (AUD-08), 52 advisories в зависимостях (AUD-09), лимиты, которые можно обойти или которые не работают за прокси (AUD-07, AUD-14), демо-сессии без лимита (AUD-05).

**Насколько оно готово к реальным пользователям?** Не готово. Нет входа в продакшене, кодов на почту, оплаты, резервных копий. Даже при закрытой бете без оплаты пользователи получат выход из аккаунта и могут заблокировать сервер файлом.

**Какие проблемы обязательно устранить до запуска:** AUD-01, AUD-02, AUD-03, AUD-04, AUD-05, AUD-06, AUD-07, AUD-08, AUD-09, AUD-10, AUD-11, AUD-13.

**Что можно оставить на последующие обновления:** AUD-12 (с оговоркой: до первых реальных магазинов), AUD-14 (если выкладка без нескольких процессов), AUD-15, AUD-16, AUD-17, AUD-18, AUD-19, AUD-20 (с CI — до запуска желательно), AUD-21, AUD-23, AUD-24, AUD-25, AUD-26, AUD-27.

**Итоговый статус: NOT READY.**
